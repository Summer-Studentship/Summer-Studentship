# C1A-P1B Regional2D OpenMP Scaling Benchmark

Generated by `tools/verification/convergence/c1a_p1b_representative_openmp_scaling.py` on the frozen C1A-R4 h600 Regional2D mesh.

## Scope

- Mesh: frozen-terrain R4 `h600`, 6554 active triangular cells.
- Serial authority: `TSUNAMI_ENABLE_OPENMP=OFF` release `tsunami_r2d_case`.
- Parallel candidate: `TSUNAMI_ENABLE_OPENMP=ON` release `tsunami_r2d_case`.
- Timing: opt-in `TSUNAMI_R2D_TIMING_JSON` scoped timers plus subprocess wall time.
- Output modes: minimal benchmark output and normal 5 s production output cadence.
- Not run: h500/h450/h400/h300 to 600 s, temporal convergence, Local3D/OpenFOAM, observations, calibration, CUDA.

## Resource Note

A 14 s h600 run, intended to approach the 500-step target, was started but proved too costly for a full placement/thread matrix in this environment. The completed P1B matrix therefore uses a 2 s h600 benchmark. It is representative in mesh size and timing instrumentation, and materially larger than the original h1000 1 s P1 smoke benchmark, but it is not production convergence evidence.

## Result

Best measured configuration:

- Threads: `8`
- `OMP_PLACES=cores`
- `OMP_PROC_BIND=spread`
- Solver-loop speedup: `1.0078x`
- End-to-end speedup: `1.0080x`
- Solver-loop parallel efficiency: `0.126`

Decision gate:

```text
C. OpenMP speedup remains negligible
```

CUDA now: not recommended. The immediate recommendation is to profile/redesign CPU execution before committing expensive fine-grid convergence runs, or reassess CUDA/HPC with representative data.

## Bottleneck Notes

In the best run, residual reduction was only about `0.062%` of solver-loop time, so the current thread-local residual reduction is not the dominant bottleneck. Boundary/exterior application was about `18.9%`, source update about `6.0%`, and face residual work about `0.86%`. CPU utilisation estimates rose only modestly with thread count, indicating that the current OpenMP face kernel is not driving broad multi-core utilisation.
